# ADR-001 — Adopt DDD Bounded Contexts with Hexagonal Architecture

**Status:** Proposed
**Date:** 2026-09-26
**Document role:** Architecture decision for Version 1. Binding design; not a C4 snapshot of the running API.
**Current runtime:** Documented in [docs/architecture](../architecture/README.md). Source contains `catalog`, `customers`, `sales-day`, `sales`, `fulfillment-output` (Load Sheet generation, invoice listing, and invoice document generation), and `alegra`. Authentication and invoice printing are not implemented yet.

## Context

The application must digitize a store-to-store sales process while preserving business rules around Sales Days, sales, customers, catalog pricing, Load Sheets, and invoices. The application will be used from both phones and PCs, but it is one application with no device-specific business role.

The main architectural risk is creating a technically organized codebase (`controllers`, `services`, `repositories`, `entities`) in which business concepts become coupled to infrastructure and changes cross unrelated areas. Current AWS Prescriptive Guidance explicitly recommends business-logic-based decomposition into bounded contexts and describes hexagonal architecture as a ports-and-adapters approach that isolates the application core from external systems. citeturn0search1turn0search4

## Decision

We will implement the backend as a **modular monolith organized around DDD bounded contexts**, with **Hexagonal Architecture inside each context**.

The initial bounded contexts are:

- `sales`
- `sales-day`
- `customers`
- `catalog`
- `fulfillment-output`

The system will not initially split these contexts into independent deployable microservices. Deployment boundaries and bounded-context boundaries are intentionally different decisions.

## Architectural Principles

### 1. Business-first decomposition

Top-level code organization follows business contexts rather than technical layers. DDD bounded contexts provide explicit model boundaries and a shared ubiquitous language. Fowler describes bounded context as a central DDD pattern for dividing large models and making their relationships explicit. citeturn0search5

### 2. Dependency inversion

The domain and application core must not depend on infrastructure implementations. External concerns interact through ports implemented by adapters. This is consistent with the original Ports and Adapters intent described by Alistair Cockburn and with current AWS guidance. citeturn0search10turn0search2

### 3. Context isolation

A bounded context must not import another context's domain entities, repositories, ORM models, or database tables directly.

Cross-context interaction must occur through explicit application contracts, queries, commands, or integration messages, depending on the use case.

### 4. Modular monolith first

The initial system is small enough that independent microservices would add operational complexity without a demonstrated need. The contexts remain independently structured so that future extraction is possible if scale or organizational boundaries justify it.

### 5. Infrastructure is replaceable

HTTP, SQL/ORM, document rendering, printing, and external integrations are adapters. Replacing an adapter must not require rewriting business rules.

## Context Responsibilities

### Sales

Owns the commercial transaction: sale lifecycle, sale items, transaction-time product identity/name and price/cost snapshots, totals, profit, logical deletion, and sale-level business invariants.

### Sales Day

Owns the daily operational container and its `OPEN`/`CLOSED` lifecycle, including current-day reopening.

### Customers

Owns customer identity and customer information required for recurring sales.

### Catalog

Owns products, brands, codes, wholesale/retail pricing information, and product search data.

### Fulfillment Output

Owns operational projections and document outputs such as Load Sheet generation and invoice rendering/printing orchestration. It does not become the owner of the Sale aggregate.

Within each context:

```text

   entities/
   value-objects/
   services/
   events/
   errors/

 application/
   use-cases/
   ports/
     inbound/
     outbound/
   dto/

 adapters/
   inbound/
     http/
   outbound/
     persistence/
     printing/
     document-rendering/

 composition/
```

This is a project convention, not a universal DDD folder standard. AWS guidance likewise recommends structures that map project organization to domain, commands, events, exceptions, models, ports, and tests rather than treating one universal folder tree as mandatory. citeturn0search4

Ports are placed at the boundary that requires the abstraction: inbound ports belong to the application boundary; outbound ports belong where the core/application requires the dependency. A port must not be created merely to satisfy a folder pattern.

## Dependency Rule

```text
Inbound Adapter
      |
      v
Inbound Application Port
      |
      v
Application Use Case
      |
      v
Domain Model
      ^
      |
Outbound Port
      ^
      |
Outbound Adapter
```

The dependency direction is toward the business core. Adapters depend on ports; the domain does not depend on adapters.

## Business Flow Alignment

The architecture is intentionally shaped around the following business state and execution flows.

### Sales Day

```text
OPEN --Close--> CLOSED
 ^                 |
 |---Reopen--------+
```

The reopen transition exists only for the current calendar day.

### Sale

```text
DRAFT --Confirm--> CONFIRMED --Logical Delete--> VOIDED
```

Confirmation allocates the invoice number once. Invoice generation and printing are downstream document operations and do not create or renumber sales.

### Transaction-time product name

The Catalog owns the canonical product identity and default name. When a seller adds a product to a Sale, the Catalog name is copied into `SaleItem.itemName`. The seller may edit that value immediately during order capture. The `productId` remains immutable.

This produces two intentionally different semantics:

- **Invoice:** uses the transaction-time `SaleItem.itemName`, because the invoice represents what was captured for that transaction.
- **Load Sheet:** aggregates strictly by `productId` and resolves the product name from Catalog. `SaleItem.itemName` is never an aggregation key.

Example:

```text
Sale A: productId=123, itemName="Green Soda", quantity=10
Sale B: productId=123, itemName="Red Soda",   quantity=5

Invoices:
  A -> Green Soda x10
  B -> Red Soda   x5

Load Sheet:
  productId=123 -> quantity 15
```

This distinction is a domain rule, not a presentation-only rule, and must therefore be represented in the backend model and tests.

## Consequences

### Positive

- Business rules remain close to the domain they describe.
- Product, sales, and Sales Day changes are easier to localize.
- Infrastructure can evolve independently from core business logic.
- Unit tests can exercise domain behavior without a database or HTTP server.
- The same business logic can be driven by the web API, automated tests, or future adapters.

### Negative

- More explicit files and interfaces than a conventional CRUD structure.
- Developers must understand bounded-context boundaries.
- Cross-context interactions require deliberate contracts.
- Adapter code introduces maintenance overhead. AWS explicitly notes that the extra separation should be justified and carefully managed. citeturn0search2

## Rejected Alternatives

### Technical-layer-first monolith

Rejected because it organizes the code primarily around infrastructure concerns and makes business boundaries less explicit.

### Microservices from day one

Rejected for Version 1 because independent deployment, networking, observability, and operational ownership would add complexity without a current requirement.

### One giant shared domain model

Rejected because sales, customers, catalog, Sales Day, and operational outputs have different responsibilities and change patterns.

### Separate frontend/backend domain duplication

Rejected as a design principle. The frontend may have presentation state and client-side view models, but it must not become a second authoritative implementation of backend business rules.

## Open Questions

- Invoice numbering is resolved: one company sequence per business date, visible digits `001` onward, allocated atomically by the database. The current allocator still emits a global `INV-` series; that runtime change is pending.
- Printer model and print mechanism are resolved: the UI prints invoice documents through the Windows print dialog on the PC. The API does not drive the printer.
- A seller may keep up to 3 sessions open at the same time, including phone and PC.
- Customers belong to the company and are not assigned to a seller or route in Version 1.
- A customer may be created during the sale visit.
- Product-name editing is confirmed: the seller can customize the sale-item name during order capture; the resulting transaction-time name is stored and used by invoice rendering only. The Load Sheet aggregates by productId and resolves the product name from Catalog. There is no separate invoice-stage name-editing workflow.
- A customer document type plus document number is unique for the whole company.
