# ADR-002 — The delivery day is a value on Sale, and Sales Day is removed

**Status:** Proposed (revised 2026-11-01)
**Date:** 2026-11-01
**Document role:** Architecture decision for the feature in [PDR-002](../pdrs/PDR-002.md). Binding design. Not a description of the running API.
**Depends on:** [ADR-001](./ADR-001.md). This decision does not add a deployable service.

## Context

PDR-002 removes the Sales Day. Sales are captured at any time, can be changed at any time, and the Load Sheet, invoices, and corrections are organized by the delivery date stored on each sale. Invoice numbers restart per delivery date.

Today `sales-day` owns three things other contexts depend on: the gate that allows sale commands, the seller who owns the sales, and the key used to list invoices. The invoice sequence is keyed by the confirmation business date.

Current sales, Sales Days, and invoice sequences are test data and will be deleted by hand. Customers and the product catalog are kept.

The risk is replacing Sales Day with an equivalent "Delivery Day" aggregate that brings back open and close under another name.

## Decision

The delivery day is **not an aggregate and not a table**. It is the `deliveryDate` value on `Sale`. Every delivery view is a query over sales.

| Concern | Owner after this decision |
|---|---|
| Whether a sale can be changed | `sales`. Always allowed by status rules only (no date window). |
| Allowed delivery dates | `sales`, from today's business date through that week's Sunday, using `BusinessDateProvider`. |
| Seller of a sale | `sales`, a `sellerId` on `Sale` from the authenticated session. |
| Invoice number | `sales`, allocated at confirm by `InvoiceNumberAllocator`, keyed by the sale's `deliveryDate`. |
| Load Sheet for a delivery date | `fulfillment-output`, read-only. Already built. |
| Invoices for a delivery date | `fulfillment-output`, read-only, filtered by `deliveryDate`. The document carries the delivery date as "Fecha de entrega". |
| Week bounds for the date range | A pure function in `sales` domain (moved from `sales-day`). |
| Returns | The existing edit and void use cases. |

The `sales-day` context is deleted: domain, use cases, routes, persistence, ACL adapters, and its tests.

## Rejected alternatives

### A Delivery Day aggregate with open/close

Rejected. It reproduces the gate the business is removing.

### Keeping Sales Day as an invisible auto-opened row

Rejected. It keeps a hidden dependency and dead error paths.

### A continuous invoice sequence

Rejected by the business. The seller reads numbers per delivery day.

### A Return document

Rejected. The seller changes or voids the sale.

## Consequences

- `Sale` drops `salesDayId` and gains `sellerId` and `captureDate`.
- `SalesDayStatusChecker`, `SalesDayBusinessDate`, `requireEditableSalesDay`, and their ACL adapters are removed from sales.
- `ConfirmSale` allocates with the delivery date.
- Re-dating a confirmed sale is one use case inside `sales` and one transaction: void the original, create a copy with a new id and the new date, confirm it with a number from the new date. No new aggregate; the copy is an ordinary `Sale`.
- `GET /invoices?salesDayId=` becomes `GET /invoices?deliveryDate=`. `SalesDayClosureQuery` leaves `fulfillment-output`.
- Test sales, sale items, invoice sequences, and Sales Days are deleted with a direct SQL command before the schema migration. The migration only changes the schema (drop `sales_days`, drop `sales.sales_day_id`, add `seller_id` and `capture_date`). Customers, catalog tables, users, and company profile are untouched.
