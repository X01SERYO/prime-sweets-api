# ADR-003 — Product administration stays in catalog and Alegra

**Status:** Proposed
**Date:** 2026-11-01
**Document role:** Architecture decision for [PDR-003](../pdrs/PDR-003.md). Binding design. Not a description of the running API.
**Depends on:** [ADR-001](./ADR-001.md).

## Context

PDR-002 carried a catalog backlog: Excel import, an inbound pull from Alegra, and Alegra sync when a product is created or deleted. That work does not change delivery days. The running API already syncs an update to Alegra after the local save, and a later Alegra failure does not undo that save.

The seller will create, update, and logically delete products from the UI. The browser must not call Alegra.

## Decision

| Concern | Owner |
|---|---|
| Product create, update, and logical delete | `catalog` |
| Sale search excluding retired products | `catalog` query used by sales. Sales does not import Alegra. |
| Excel import and Alegra inbound pull | `catalog` with the `alegra` outbound port |
| Alegra HTTP | `alegra`. Called after the local commit. A failure is logged and does not roll back. |

## Rejected alternatives

### A catalog context inside sales

Rejected. Products are not a delivery-day concept.

### Calling Alegra from the UI

Rejected. The client talks only to this API.

## Consequences

- Physical `DeleteProduct` is replaced by a logical delete.
- Delivery-day documents do not specify this feature. See [PDR-002](../pdrs/PDR-002.md).
