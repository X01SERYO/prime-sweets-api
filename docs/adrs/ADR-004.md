# ADR-004 — Retail sales are a separate bounded context

**Status:** Proposed
**Date:** 2026-11-14
**Document role:** Architecture decision for [PDR-004](../pdrs/PDR-004.md). Binding design. Not a description of the running API.
**Depends on:** [ADR-001](./ADR-001.md), [ADR-002](./ADR-002.md).

## Context

The `sales` context models a wholesale sale: customer required, delivery date in the current week, `DRAFT → CONFIRMED → VOIDED`, daily invoice number, and wholesale price snapshot. Load Sheet and invoices in `fulfillment-output` read those sales.

A retail sale has none of that. It has no customer, no invoice, no delivery date, no lifecycle, and it uses the retail channel. Its identity is the business day, and its editability depends only on whether that day is today.

## Decision

Create a new bounded context `retail-sales` with aggregate root `RetailDay` and child entity `RetailDayItem`.

| Concern | Owner |
|---|---|
| Retail day, its rows, totals, and the "only today" rule | `retail-sales` |
| Today in `America/Bogota` | `BusinessCalendar` port, same adapter already used by `sales` |
| Retail price, retail cost, code, brand, and name snapshot | `RetailProductSnapshotProvider` port, implemented by an ACL in `src/apps/dependency-injection/acl/` over `catalog` |
| Product search for the picker | Existing `GET /products/search` in `catalog` |

`retail-sales` does not import `sales`, `fulfillment-output`, `customers`, or `alegra`. `fulfillment-output` does not read retail tables.

### Storage: summary row with a daily draft

Only today's detail matters. `retail_days` holds one row per day with final summary columns, plus a `jsonb` draft (`open_items`) that exists only for today and is set to `NULL` lazily once the day is past. Summary columns are written in the same statement as the draft, so discarding the draft never loses a total. See SPEC-004 §2.

## Rejected alternatives

### A `retail_day_items` detail table

Rejected. It keeps rows nobody reads after the day ends (about 40 per day), needs a purge job, and a delete-heavy table bloats in PostgreSQL. The draft in one `jsonb` column is rewritten in place and compacted with a single `UPDATE`.

### Keeping today's detail only in the browser (localStorage)

Rejected. It is lost when the session closes or the seller changes device, which the business requires to survive.

### A scheduled job to purge at midnight

Rejected for now. Lazy compaction at the start of every retail use case needs no scheduler, and totals are already final, so a late compaction is harmless.

### A `channel` column on `sales`

Rejected. `customer_id` is `NOT NULL`, the delivery-date range, invoice numbering, the confirm step, the Load Sheet, and the invoice list would all need a retail branch. Every existing wholesale query would have to filter the channel, and a missed filter would mix retail into invoices and the Load Sheet.

### A dummy "counter" customer on wholesale sales

Rejected. It would allocate invoice numbers, enter the Load Sheet, and still use wholesale prices.

### Computing the day only in the client

Rejected. The "only today" rule must hold even when a client sends a change for an earlier day.

## Consequences

- One new table, `retail_days`, with its own migration. No detail table.
- A past retail sale cannot be audited by product.
- A new route group `/retail-days`.
- Wholesale code paths do not change.
- Cross-day retail reporting, if requested later, reads only `retail-sales`.
