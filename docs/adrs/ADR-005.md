# ADR-005 — Purchase orders are a separate context; only the last order keeps lines

**Status:** Proposed
**Date:** 2026-11-16
**Document role:** Architecture decision for [PDR-005](../pdrs/PDR-005.md). Binding design. Not a description of the running API.
**Depends on:** [ADR-001](./ADR-001.md).

## Context

A pedido is not a sale. It has a supplier, a catalog cost, and no customer, delivery date, invoice, or retail day. Putting it on `sales` or `retail-sales` would force every existing query to exclude it.

The seller compares a new order only with the previous one. A line table that grows with every order would keep rows nobody reads. Retail already chose a summary row plus a draft that is discarded ([ADR-004](./ADR-004.md)). Pedidos need a similar bound: detail for the latest order only, and a cheap way to show "last quantity" without reading that document on every new sheet.

## Decision

Create a bounded context `purchasing` with two aggregates: `Supplier` and `PurchaseOrder`.

| Concern | Owner |
|---|---|
| Supplier name and the products linked to that supplier | `Supplier` |
| Last quantity, last unit cost, and last item name per supplier product | Columns on the supplier–product link, written only when an order is saved |
| The saved order header and, only while it is the latest, its lines | `PurchaseOrder` |
| Code, brand, name, and current cost for the sheet | `PurchaseProductReader` port, implemented by an ACL over `catalog` |

`purchasing` does not import `sales`, `retail-sales`, `customers`, `fulfillment-output`, or `alegra`.

### Storage

- `suppliers` — one row per supplier.
- `supplier_products` — one row per supplier and product. Holds `last_quantity`, `last_unit_cost`, and `last_item_name` (all nullable until that product has been on a saved order). The line name itself follows the wholesale `catalogName` / `itemName` rule.
- `purchase_orders` — one row per saved order: supplier, timestamp, `line_count`, `total_cost`, and `lines jsonb` **only on the latest order of that supplier**.

Saving an order, in one transaction:

1. Inserts the new `purchase_orders` row with its lines.
2. Sets `lines = NULL` on the previous order of that supplier. Header totals stay.
3. Overwrites `last_quantity`, `last_unit_cost`, and `last_item_name` on each included supplier product, and clears those hints on supplier products that were omitted this time.

Opening a new sheet reads `supplier_products` plus the catalog ACL. It does not read `purchase_orders.lines`.

A partial index on `purchase_orders (supplier_id) WHERE lines IS NOT NULL` keeps the "one detailed order per supplier" lookup small.

## Rejected alternatives

### A `purchase_order_items` table for every order

Rejected. The business only reads the last order. The table would grow without a reader, and a new sheet would either scan it or still need a denormalized last quantity.

### Reading the previous order's `jsonb` to paint last quantities

Rejected. It couples the sheet to history and forces a parse of the whole previous document. The link row is one indexed read per supplier.

### Keeping the working sheet only in the browser and never storing last quantities

Rejected. The last order must survive a new session and another device. The unsaved sheet itself is not stored (PDR-005 OQ-P7); the last **saved** quantities are.

### A `channel` or `kind` on `sales`

Rejected. Same reasons as retail in ADR-004: customer, invoice, and Load Sheet would all need a branch they do not have.

## Consequences

- Three new tables and a new route group `/suppliers` and `/purchase-orders`. See [SPEC-005](../specs/SPEC-005.md).
- An older order cannot be audited by product. Date, supplier, line count, and total remain.
- Catalog, sales, retail, and fulfillment schemas do not change.
