# PDR-005 — Supplier purchase orders (Pedidos)

**Status:** Proposal
**Language:** English
**Scope:** Suppliers, the products each supplier sells, and a purchase order that compares against the previous purchase order only.

**Term:** Spanish **pedido** / **Pedidos** translates as **purchase order** / **Purchase orders**. Do not call it an order in English: that word is already the customer sale. Code and HTTP use `PurchaseOrder` and `/purchase-orders`. The Spanish navigation label stays **Pedidos**.
**Document role:** Product design requirement. Business source of truth for this feature. Not a description of the running API.

## 1. Purpose

The business buys from suppliers. Today that list is outside the app. The seller needs a **Pedidos** place to register a supplier, choose which catalog products that supplier provides, and write a new purchase order.

On a new order the seller must see, for each of that supplier's products: code, brand, product name, unit cost, and the quantity from the **last saved order** when one exists. They type the new quantity (and an optional flavor or short description, the same idea as an extra name on a wholesale line). Each row shows its cost total, and the order shows a grand total.

They do not look up older orders line by line. Keeping every historical line would store data nobody reads. Only the last order per supplier keeps its lines.

## 2. What the seller can do

1. Open **Pedidos** from the main navigation.
2. Create a supplier (a name). Edit the name. A supplier is not a customer.
3. Choose the products that supplier sells, by the same product search used elsewhere (name, brand, or code). A product may belong to more than one supplier. Removing a product from the supplier hides it on the next order; it does not change a saved order.
4. Start a new order for one supplier. The sheet lists every product currently linked to that supplier, even if the new quantity stays empty.
5. Read, per row: code, brand, product name, unit cost, and last quantity (blank when that product was not on the previous saved order, or when the supplier has no saved order yet).
6. Type a new quantity and, optionally, a short note (flavor or other description).
7. See line cost (`unit cost × quantity`) and the order total (sum of line costs). Rows left blank or at zero are not part of the order.
8. Save the order once. After save, this order is the "last order" for that supplier. The previous order keeps its date and total and loses its lines.

## 3. Rules

- **One supplier, many products.** The order sheet is the supplier's current product list, not a free search of the whole catalog.
- **Unit cost** is the catalog cost of the product at save time (the `cost` on the wholesale price row). It is snapshotted onto the line. A later catalog change does not change a saved order. A product with no cost cannot be saved on an order.
- **Last quantity** is the quantity saved for that product on the supplier's previous order. It is a hint, not a default: the new quantity input starts empty. The seller does not edit the last quantity.
- **New quantity** is an integer ≥ 1 when the row is included. Empty or zero means "not on this order".
- **Note** is optional, at most 80 characters, stored on the line. It does not change the catalog product name.
- **Order total** is the sum of rounded line costs. An order with no included line cannot be saved.
- **Only the last saved order per supplier keeps lines.** Older orders keep supplier, date, line count, and total cost. There is no screen that restores lines of an older order.
- Saving is a single action. There is no draft left on the server if the seller leaves the sheet. The last saved order stays as it was.
- A purchase order does not change stock, does not create a sale, does not create an invoice, and is not sent to Alegra.
- Two people saving the same supplier at the same moment is not a business case. The last save wins. No version column.

## 4. Out of scope

- Inventory, receiving, partial deliveries, and backorders.
- Supplier price lists that differ from catalog cost, discounts, and tax.
- Editing or voiding a saved order.
- Line history across more than the last order.
- Purchase orders per branch or per seller. One business-wide list.
- Customers, wholesale sales, retail days, Load Sheet, and invoices.

## 5. Acceptance criteria

- **Pedidos** is a main-navigation entry, separate from Por mayor, Detal, Cargue, and Productos.
- A supplier can be created and given a set of catalog products.
- A new order lists those products with code, brand, name, unit cost, last quantity (when the previous order had that product), an input for the new quantity, an optional note, and the line cost.
- The order total equals the sum of line costs of rows with a quantity ≥ 1.
- After save, opening a new order shows the quantities just saved as "last quantity".
- The previous order still appears as a header (date, supplier, total) and no longer returns lines.
- A product with no catalog cost is rejected on save.
- Wholesale sales, retail days, invoices, and the Load Sheet behave as before.

## 6. Decisions

| Id | Question | Decision |
|---|---|---|
| OQ-P1 | Which cost? | Catalog wholesale `cost`, snapshotted at save. |
| OQ-P2 | Default the new quantity from the last order? | No. Last quantity is read-only. The input starts empty. |
| OQ-P3 | Decimal quantity? | Integer ≥ 1, or omit the row. |
| OQ-P4 | How far back can lines be read? | Last saved order per supplier only. |
| OQ-P5 | Where is the last quantity stored? | On the supplier–product link, overwritten at save. The new order does not scan old lines. |
| OQ-P6 | Note / flavor? | Optional line note, max 80 characters, same role as an extra name on a wholesale line. |
| OQ-P7 | Unsaved sheet? | Not stored. Only **Guardar** creates an order. |
| OQ-P8 | Edit a saved order? | No. |
